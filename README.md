基于SpringBoot+MyBatis的拍卖场次智能调度与竞拍系统 设计文档
1. 项目背景与目标
1.1 背景
传统拍卖系统多为单场次、固定排期，缺乏对拍卖师、拍品、时间、用户注意力等多资源约束的调度能力；同时竞拍涉及保证金、尾款、违约、流拍等复杂资金状态，单纯CRUD无法保证一致性。

1.2 目标
实现拍卖场次的智能排期：拍卖师、拍品、时间、用户四维冲突检测与半自动排期。

实现完整竞拍交易链路：出价、保证金、延时竞价、竞拍结束、订单、尾款、违约、流拍再排。

保证资金最终一致：短事务+事件驱动+本地消息表+定时对账。

模拟分布式边界：单机部署，按服务边界拆分模块，体现跨机器设计思想。

2. 需求分析
2.1 角色
买家：浏览、关注、交保证金、出价、代理出价、付尾款、评价。

卖家：提交拍品、定价、选择场次、查看结算。

拍卖师：主持场次、控制节奏、触发延时/结束。

管理员：审核拍品、审批排期、处理风控与争议、对账。

系统：排期调度、风控标记、资金处理、通知。

2.2 核心用例
拍品提交→审核→鉴定→排期→预展→竞拍→成交/流拍→支付→交割→评价。

排期冲突检测：同一拍卖师、同一拍品、同一时间段、同一用户关注冲突。

出价：校验资格、冻结保证金、更新当前价、记录出价、延时判断。

竞拍结束：确定赢家、生成订单、解冻未成交者保证金、流拍再排。

资金：保证金冻结/解冻/扣除、尾款支付、佣金结算、退款、对账。

3. 业务建模（网状约束）
3.1 核心实体
用户、卖家、拍卖师、拍品、竞拍场次、时间段、出价记录、保证金账户、订单、支付流水、状态流水、排期记录。

3.2 关键约束
硬约束：同一拍卖师同一时间只能主持一场；同一拍品只能在一个场次；同一时间段同一虚拟直播间只能承载一场；场次时间不能重叠。

软约束：黄金时段优先高价值拍品；同类拍品错开；用户关注冲突尽量少；拍卖师连续场次间隔休息。

资金约束：保证金不足不能出价；尾款超时违约；退款不能超过已付金额。

3.3 排期算法
冲突检测：规则+唯一索引。

半自动排期：贪心+回溯+评分函数，生成候选方案，管理员确认。

动态顺延：上一场延时触发时，按规则顺延下一场或强制切割。

4. 系统架构
4.1 逻辑分层
接入层：Web/API。

应用层：拍卖服务、排期服务、资金服务、订单服务、风控服务、通知服务。

领域层：状态机、约束校验、领域事件。

基础设施：数据库、本地消息表、事件队列、定时任务、对账。

4.2 单机模拟分布式
模块间不直接跨库join，通过领域事件通信。

每个服务本地事务写业务+消息表。

事件循环单线程交错处理，失败停状态，定时补偿。

预留接口，可平滑拆分为多机部署。

5. 核心流程设计（短事务+状态机+事件驱动）
5.1 出价流程拆分
步骤	事务内容	锁/防重	事件
1	校验资格，写出价记录（待冻结）	唯一索引防重	BidCreated
2	冻结保证金，写资金流水	用户账户行锁	DepositFrozen
3	更新拍品当前价、领先者	乐观锁+状态校验	PriceUpdated
4	出价记录生效	状态机校验	BidEffective
5	通知、热度更新	异步	无
5.2 竞拍结束流程
标记结束（分布式锁+状态机）→ 确定赢家 → 生成订单（唯一索引）→ 解冻未成交者 → 通知。

5.3 状态机设计
竞拍状态：待开始→进行中→延时中→已结束→已成交/流拍。

出价状态：待校验→待冻结→已冻结→已生效→已失效/已成交。

订单状态：待生成→待支付→已支付→待发货→已完成/已取消/退款中/退款成功。

6. 一致性与锁设计
6.1 原则
能不用锁就不用：唯一索引、乐观锁、状态机校验、幂等键优先。

锁粒度按业务边界：出价锁拍品行，资金锁用户账户行。

固定锁顺序：用户账户→拍品→订单→流水。

短锁+长状态：锁只用于改状态，后续靠事件推进。

跨服务最终一致：本地消息表+定时补偿+对账。

6.2 关键场景
出价：乐观锁 where id=? and current_price=? and status='进行中'。

保证金：update account set frozen=frozen+? where user_id=? and balance>=? + 流水唯一索引。

排期：(auctioneer_id, start_time) 唯一索引防冲突。

支付回调：pay_no 唯一索引幂等。

7. 跨机器问题与模拟方案
7.1 跨机器典型问题
超时、乱序、分区、消息丢失、重复消费、本地事务锁不住远程、状态不同步、分布式锁失效、脑裂、无全局时钟、部分失败、链路难追踪。

7.2 单机模拟方案
服务模块化，数据库逻辑分库。

本地消息表：业务与消息同事务。

事件循环单线程交错处理。

消费端幂等：唯一索引+幂等键。

定时对账：订单、支付、资金流水三方比对。

Trace ID 贯穿全链路。

8. 数据库设计要点
用户、拍卖师、卖家、拍品、场次、排期、出价记录、保证金账户、资金流水、订单、支付流水、状态流水、消息表、对账差异表。

关键唯一索引：出价防重、支付防重、排期冲突、消息幂等。

状态字段与版本号：乐观锁、状态机校验。

9. 接口设计（示例）
POST /bid：出价，返回受理状态。

POST /schedule/generate：生成排期候选。

POST /schedule/confirm：确认排期。

POST /auction/end：结束竞拍。

POST /pay/callback：支付回调（幂等）。

GET /reconcile/diff：对账差异查询。

10. 测试与验证
单元测试：状态机转换、约束校验、幂等。

集成测试：出价全链路、竞拍结束、支付回调重复、排期冲突。

异常测试：最后一秒出价、消息重复、服务重启恢复、对账差异补偿。

压测：出价接口QPS、响应时间、错误率；排期算法耗时。

11. 进度安排（建议）
第1-2周：需求、建模、数据库设计。

第3-4周：基础CRUD、权限、拍品/场次管理。

第5-6周：排期冲突检测+半自动排期。

第7-8周：出价、保证金、状态机、短事务事件驱动。

第9-10周：竞拍结束、订单、支付、尾款、违约、对账。

第11-12周：前端、测试、压测、文档、答辩准备。
